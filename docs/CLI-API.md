# fyl.at HTTP API

The public base is `https://fyl.at`. Requests work with plain curl and browsers; no accounts, cookies or R2 credentials, and no browser challenge except the Turnstile check of the report form ([Turnstile](#turnstile)). The `fyl` command is described in [CLI.md](CLI.md), the Cloudflare side in [OPERATIONS.md](OPERATIONS.md).

## CLI downloads

The native binaries (`cli-rs/`, Rust) are published per version: `/cli/<version>/fyl-<os>-<arch>` for macOS (x86_64, arm64; macOS 11+) and Linux (x86_64, arm64; static musl), with `/cli/<version>/SHA256SUMS`. Files under `/cli/<version>/` never change and are cached as immutable for a year. `/cli/latest` (plain text, the current version) and `/cli/version.json` (`{name, version, path, files: {name: sha256}}`) name the current version and are cached for 60 seconds; the CLI's daily [update notice](CLI.md#update-notice) reads `version.json`, and `fyl update` the binary it names, checked against `version.json` and `SHA256SUMS` (from 2.5.0). The previous version's folder is kept as well and older ones are removed; 2.3.0 was the first versioned folder. The public release started the numbering over at 1.0.0: fyl counted 2.0.0 to 2.5.1 before, and the new numbering never uses those versions. A CLI of the old numbering compares versions by number, so 2.5.0 would read 1.0.0 as older: `/cli/version.json` answers a User-Agent `fyl-cli/2.0.0` to `fyl-cli/2.5.0` with the index of 2.5.1 (also at `/cli/bridge.json`, same shape), the bridge, whose folder stays for good. 2.5.1 takes 1.0.0 and every later release as newer, so `fyl update` goes 2.5.0 → 2.5.1 → current. Every other client gets the current version; since the answer depends on the User-Agent, it is sent `Cache-Control: private, max-age=60` and `Vary: User-Agent`. The unversioned paths that installers before 2.3.0 fetch, `/cli/fyl-<os>-<arch>` and `/cli/SHA256SUMS`, answer 302 to the current version (`dist/_redirects`).

`curl -fsSL https://fyl.at/cli/install | sh` reads `/cli/latest`, downloads the binary and `SHA256SUMS` from that version's folder, checks the checksum and that the binary reports that version, and installs `/usr/local/bin/fyl` (sudo only if needed; `FYL_INSTALL_DIR` to override). It never writes to shell profiles. `FYL_BASE_URL` points it at another deployment.

## Routes

All API responses are JSON objects with `Cache-Control: no-store`. Errors are `{error, code}` with a fitting status ([errors](#errors)); 429 and 503 carry `Retry-After`. Methods other than those listed get 405. Mutations from another origin are refused: a cross-origin `Origin` or `Sec-Fetch-Site: cross-site` gets 403 (clients without these headers, like the CLI, are not affected).

| Route | Method | Input | Success |
| --- | --- | --- | --- |
| `/api/health` | GET | none | `{service, status, maxFileBytes, partSize, e2ee}`; `e2ee`: whether new [encrypted uploads](#end-to-end-encrypted-transfers) are taken |
| `/config.js` | GET | none | `window.FYL_CONFIG = {maxFileBytes, e2ee}` for the web client, plus `turnstileSiteKey` while the report form's [Turnstile check](#turnstile) is on |
| `/api/upload/init` | POST | JSON (≤ 8 KiB) `filename`, `size`; optional `expiresIn` (seconds, default 86400), `oneTime` (default false), `partSize` (52428800), `clientKey`, `password` ([rules](#passwords)); optional `Idempotency-Key` header. An [encrypted upload](#end-to-end-encrypted-transfers) sends `mode: "e2ee"`, the encrypted size and `e2ee: {head, meta}` instead of a `filename` | 201 `{uploadId, key, url, mode}`; `url` is the final download link, which [works at once](#early-links); `mode` is `raw` or `e2ee` |
| `/api/upload/pin` | POST | Encrypted uploads only: JSON `{uploadId, partNumber, md5}` (32 lowercase hex); `Authorization: Bearer <key or resume token>` | 200 `{partNumber, md5}` ([pins](#end-to-end-encrypted-transfers)) |
| `/api/upload/part` | PUT | Binary body with `Content-Length` (≤ 50 MiB); `Authorization: Bearer <key or resume token>`; query `uploadId`, `partNumber`; an encrypted upload's part also `Content-MD5` equal to its pin | 200 `{etag}` (the part's MD5 in production) |
| `/api/upload/status` | GET | `Authorization: Bearer <key or resume token>`; query `uploadId` | 200 `{status, access, name, size, partSize, expiresIn, once, uploadDeadline, url, mode, parts: [{partNumber, size, etag}]}`; `access` is `owner` for the key, `resume` for the resume token; an encrypted upload adds `e2ee: {head, meta}` and `pins: [{partNumber, md5}]` and has `name: null` |
| `/api/upload/complete` | POST | JSON (≤ 2 MiB) `uploadId`, `key` (or the resume token), `parts: [{partNumber, etag}]` in order | 200 [receipt](#receipt) |
| `/api/upload/abort` | POST | JSON (≤ 8 KiB) `uploadId`, `key` (or the resume token) | 200 `{aborted: true}`; 409 once completed, completing or used up |
| `/api/transfers/:id` | GET | Optional `Authorization: Bearer <management key>`, or `Authorization: Basic` with a protected transfer's password | Public metadata (`id`, `name`, `size`, `createdAt`, `expiresAt`, `minutes`, `once`, `downloads`, `state`, `protected`, `url`, `mode`, `owner: false`; an encrypted transfer adds `e2ee`), or the [owner view](#owner-api) with the key; both with `serverTime` (ms). The right password as Basic adds a protected raw file's name and an encrypted transfer's `e2ee` (a wrong one: 401 `password_wrong` or 429 `password_paused`, JSON, never a challenge) |
| `/api/transfers/:id` | PATCH | Management key; JSON (≤ 1 KiB) `{expiresIn}` or `{clearPause: true}` | The owner view with `serverTime` |
| `/api/transfers/:id` | DELETE | Management key | 200 `{deleted: true}` |
| `/api/transfers/:id/done` | POST | none | 204; closes an encrypted one-time link at once when sent from the network of its download session, and changes nothing otherwise |
| `/api/reports` | POST | JSON (≤ 16 KiB), [fields](#reports); on `report.fyl.at` (the form) or `fyl.at` | 201 `{case, received, fileAvailable}` |
| `/d/:id[/:name]` | GET, HEAD | Optional single `Range`; protected files: Basic Auth or `?grant=` | The file as an attachment, or the [download page](#download-pages) for browsers and preview bots; 503 `uploading` while the [upload runs](#early-links). An encrypted file goes only to `?dl=1`, a grant or Basic (409 `encrypted` otherwise). The id ends at the first `/` or `%23` |
| `/d/:id[/:name]` | POST | Form field `password` from the download page | The download page, unlocked or with the reason ([passwords](#passwords)) |
| `/d/:id/:name?preview=1` | GET, HEAD | Known link-preview bots only | The [image preview](#link-previews), or 404 |
| `/`, `/privacy` | GET, HEAD | none | Static pages (the upload page, the privacy notice) whose Content-Security-Policy the Worker sets: scripts and workers only from fyl's own script paths, never `'self'` (which would admit scripts Cloudflare injects under `/cdn-cgi/`). The `/d/` pages and the report form (next row) get the same kind of policy |
| `/report` | GET | none | 302 to `https://report.fyl.at/` with the query kept (since 2.4.0). The report host serves the form at `/` (its policy also allows `https://challenges.cloudflare.com`), its files, `/config.js` and `POST /api/reports`, and 404 for everything else |
| `/api/stats` | GET | Admin host only, query `range` | The dashboard's [statistics](#statistics); 404 on `fyl.at` |
| `/api/billing` | GET | Admin host only | The dashboard's [estimate of the open Cloudflare bill](#billing-estimate); 404 on `fyl.at` |

`uploadId` is the public transfer id, not R2's multipart upload id, and `key` is a random capability for one transfer, not an R2 object key. A filename is 1 to 1024 UTF-8 bytes, not only dots, and contains no `/`, `\`, control characters (C0 and C1), lone surrogates or line and paragraph separators (U+2028/U+2029); bidi controls (U+061C, U+200E/U+200F, U+202A–U+202E, U+2066–U+2069) are dropped from it (apps such as WhatsApp put them around phone numbers), so a name can't disguise its extension. Files are non-empty and at most 50 GB (`MAX_FILE_BYTES`, 50 × 1024³ bytes), split into 50 MiB parts with a smaller last one; lifetimes run from 300 to 604800 seconds and count from the completion.

`clientKey` must be 43 URL-safe characters encoding 32 random bytes; it becomes the upload's key. Combined with an `Idempotency-Key` of 16–128 URL-safe characters, the transfer id is derived from both (`SHA-256(clientKey + ":" + Idempotency-Key)`, hex), so an identical init retry returns the same session and different metadata gets 409. Without both the id is random. The CLI and the web client send both. Never use a shared or predictable client key.

<a id="resume-token"></a>Every upload also accepts a resume token: `base64url(SHA-256("fyl-resume:" + key))` without padding, 43 characters. The server keeps only its hash. The part, status, completion and abort routes take it wherever they take the key; `/api/transfers/:id` doesn't (403 `denied`, like a wrong key), so the token can't delete the file or change its expiry, and a completion made with it returns no `managementUrl` or `deleteToken`. Uploads created before 2.1.2 accept only the key.

Every admitted part attempt writes its own R2 part number (a "slot"), so a late attempt can't overwrite a confirmed part; responses and the completion manifest use the logical part numbers. A part whose slots all hold attempts still running answers 503 `part_busy` with `Retry-After: 10`. An attempt the Worker reports more than 6 hours after its admission answers 503 `lease_expired`; send the part again. A part gets 20 admitted attempts (refused ones don't count), then 409 `part_limit`, which ends the upload. The key or resume token goes only in the `Authorization` header: a `key` in the query of a part or status request, as CLI 2.0 sent it in the part URL, authorises nothing (400 without a header key, 403 `denied` next to a wrong one).

## Errors

Clients classify every answer by status and code (`tests/vectors/errors.json`, read by the server, browser and Rust tests):

| Class | When | What clients do |
| --- | --- | --- |
| retry | no answer or a broken connection, 408, 429, 500–504 (any 5xx) | try again with backoff and jitter, honouring `Retry-After` up to 60 s; once retries are used up the upload stays resumable |
| permanent | any other 4xx, and `part_limit` with any status | stop; an upload is aborted (CLI and browser) |
| unclear | `/api/upload/complete` answered 2xx but the body is unreadable, not JSON or not a valid [receipt](#receipt), or the connection broke after the request was sent | repeat the same completion (it is idempotent) up to 5 times with backoff, then read `/api/upload/status` and complete once more if it says `ready` or `completing`; never drop the recovery data |

| Status | `code` | Class | Meaning |
| --- | --- | --- | --- |
| 400 | `request_failed` | permanent | Invalid input; the message says what |
| 401 | `denied` | permanent | Operator token missing or wrong |
| 401 | `password_wrong` | permanent | A wrong password as Basic on `GET /api/transfers/:id`; the body has `triesLeft` (no `WWW-Authenticate`) |
| 403 | `denied` | permanent | Wrong or missing private key, or a resume token on `/api/transfers/:id` |
| 403 | `request_failed` | permanent | A cross-origin or cross-site mutation |
| 403 | `e2ee_disabled` | permanent | This server takes no new encrypted uploads at the moment (init with `mode: "e2ee"` only) |
| 403 | `quarantined` | permanent | The file is unavailable while a report about it is reviewed |
| 403 | `turnstile_failed` | permanent | The report form's Turnstile token is missing, refused, expired or for another host or action (`/api/reports` only, while Turnstile is on); the page gets a new token, then send again |
| 403 | `hotlink` | permanent | Another site's page loaded a download link as a resource ([hotlink protection](#hotlink-protection)) |
| 404 | `not_found` | permanent | No such transfer, route or report; a malformed `/d/` id; operator routes without a valid secret |
| 409 | `request_failed` | permanent | Conflicting state: init metadata, completion manifest or completion parts don't match |
| 409 | `part_limit` | permanent | This part reached its 20 attempts; the upload can't be resumed |
| 409 | `upload_running` | permanent | The sender asked to change an upload that is still running |
| 409 | `part_changed` | permanent | An encrypted part's pin or `Content-MD5` differs from its pin: the file changed; start a new upload |
| 409 | `head_mismatch` | permanent | The completed encrypted file doesn't start with the `head` its init sent; the object is deleted and the upload failed |
| 409 | `encrypted` | permanent | An encrypted file asked for without `?dl=1`, a grant or Basic; a plain-text hint names `fyl download` and nothing was opened |
| 410 | `request_failed` | permanent | The upload session is closed |
| 410 | `expired`, `consumed`, `deleted`, `removed` | permanent | The transfer is closed: its lifetime ended, the one-time link was used (or another network holds its session), the sender deleted it, the operator took it down |
| 410 | `aborted` | permanent | The upload never completed (cancelled, failed, or past its 24-hour window) |
| 410 | `unavailable` | permanent | The link is open but the stored file is missing |
| 413 | `request_failed` | permanent | File or body too large |
| 415 | `request_failed` | permanent | Wrong content type |
| 416 | `request_failed` | permanent | A range that can't be served (several ranges, or one outside the file) |
| 429 | `rate_limited` | retry | A per-network rate limit ([routes](OPERATIONS.md#rate-limits)) |
| 429 | `storage_capacity`, `daily_budget` | retry | The global storage budget, or the global daily volume or upload count, is full |
| 429 | `network_budget` | retry | This network's daily upload count (500) is used up (init only) |
| 429 | `network_uploads` | retry | This network runs 50 unfinished uploads (init only) |
| 429 | `network_bytes` | retry | This network's daily volume (250 GB) is used up; the upload stays resumable |
| 429 | `network_storage` | retry | The network that started the upload stores 250 GB already; frees when one of its files is deleted or expires |
| 429 | `report_limit` | retry | This network filed 50 reports today (`/api/reports` only) |
| 429 | `password_paused` | permanent | Too many wrong passwords as Basic on `GET /api/transfers/:id`; like `part_limit`, any status with this code is final: wait for `Retry-After` or `pausedUntil` |
| 500, 502, 504 | — | retry | Server or gateway error |
| 502 | `part_corrupt` | retry | An encrypted part was stored with another MD5 than its pin; send the same bytes once more, then stop (the upload stays resumable) |
| 503 | `temporarily_unavailable` | retry | Storage or a Durable Object failed, or Cloudflare's siteverify gave no usable answer for a report |
| 503 | `request_failed` | retry | The upload is still being created, or its completion still runs |
| 503 | `uploads_paused` | retry | The operator paused uploads; the upload stays resumable |
| 503 | `part_busy` | retry | Every slot of the part holds an attempt still running; `Retry-After: 10` |
| 503 | `lease_expired` | retry | A part attempt was reported after its 6-hour lease; send it again |
| 503 | `misconfigured` | retry | A Worker secret is missing, or Cloudflare rejects `TURNSTILE_SECRET` (`/api/reports` only); retrying helps once the operator fixes it |
| 503 | `uploading` | retry | A download link whose upload hasn't completed; `Retry-After: 10`, the body adds `received` and `size` |
| 503 | `unsupported_mode` | retry | The transfer's mode needs a newer server (`/d/` only); nothing was opened or counted |

Operator and report routes add a few permanent 400 and 409 codes, listed with them. The server no longer sends 426 `upgrade_required` (until 2.2.0 the answer to a key in the part URL); the vectors keep it as permanent. `/d/` links answer browsers with the [download page](#download-pages) instead of these JSON errors, and a protected file's 401 and paused 429 are plain text ([passwords](#passwords)).

The browser makes up to 3 attempts per request (5 for the completion) with pauses doubling from 1 s and ±20 % jitter; the CLI makes up to 3 attempts per request with pauses of 2 s and 4 s plus up to 20 % jitter. Both wait for `Retry-After` instead when it is given, up to 60 s.

## Receipt

A client treats an upload as done only when the 2xx answer to `/api/upload/complete` is a JSON object with:

- `url`: a string matching `^https?://[^/]+/d/[A-Za-z0-9_-]{43,64}(/[^?#]*)?$`;
- `transferId`: equal to the session's `uploadId`;
- `expiresAt`: a finite number (ms);
- `size`: equal to the file's size;
- `managementUrl`: a string, when the client completed with the management key and asked for it (the website always does, the CLI with `--manage`).

Anything else is unclear (see above). `tests/vectors/receipts.json` holds valid and invalid cases. The receipt also carries `id`, `name`, `createdAt` (the completion time), `minutes`, `once`, `downloads`, `state`, `protected` and `mode`; `url` has no name segment for a protected file. An encrypted upload's receipt has `name: null`, `url` `/d/<id>` and `size` C, the stored size; its client builds the shared link `<its own origin>/d/<id>#<KEY>` itself. A completion made with the key adds `managementUrl` (`<base>/#manage/<id>/<key>`) and `deleteToken` (the same key). Repeated completions with the same parts get the same receipt.

## Upload semantics

Completion is idempotent for the same part manifest, including recovery when R2's completion succeeded before the answer was lost. The parts must match the server's confirmed parts exactly, numbers and ETags, in order; a conflicting manifest gets 409. If R2's completion fails, the transfer reopens for upload (unless R2 did complete it), so a retry completes at once. Abort revokes an incomplete upload; it answers 409 for one that is completed, completing or used up, so it never deletes a file, and 200 (keeping the public reason) for one that is already closed. The private `DELETE` removes a completed file, also an upload still running and a file under review; on a closed transfer it succeeds and keeps the reason. A closed transfer answers 410 with its reason for 7 days after cleanup, then 404; a takedown answers 410 `removed` for good.

Upload budgets ([semantics](ARCHITECTURE.md#budget-semantics)): at init the declared size must still fit the global storage and daily caps and the network's daily volume (250 GB, counted for the network sending the parts) and stored bytes (250 GB, counted for the network that started the upload), and the network may have at most 500 uploads admitted today and 50 running. Each part then needs room for its own bytes in the same byte caps; bytes count once R2 confirmed them, never for a declared size alone. A network for these caps is an IPv4 address or an IPv6 /56. A part refused by a cap answers 429 and can be sent again later; it doesn't count against the attempt limit.

## Downloads

<a id="one-time-download-sessions"></a>**One-time links** open a download session on the first GET or range request. Only the network that opened it (a per-transfer hash of its IPv4 address or IPv6 /64) may continue: it can resume and split the download with single byte ranges. A complete download in one response (a plain GET or a range covering the whole file, such as `bytes=0-`) closes the link right away (an encrypted file's doesn't: [see there](#end-to-end-encrypted-transfers)); otherwise it closes 15 minutes after its last response ended (a response still streaming keeps it open) or after a [password pause](#passwords) that refused its network ended, whichever is later, and 24 hours after it opened at the latest. HEAD, pages and metadata never open a session; other networks get 410 `consumed`. The claim is persisted before R2 is read. Every download supports one byte range per request; a range that can't be served gets 416 before a session opens or a download is counted. Responses are attachments with `application/octet-stream`, `nosniff`, `no-referrer`, `private, no-store`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cross-Origin-Resource-Policy: same-origin`; Every file response carries `Content-Length` (one-time ones too, since 2.4.0), and HEAD sends the same headers (`Content-Length`, `Accept-Ranges`, `ETag`) without a body. Deletion and expiry block new requests; open streams and downloaded bytes can't be recalled.

<a id="download-pages"></a>**Download pages.** A `/d/` request is a page request when it is a GET with `Accept` containing `text/html`, no `Range` and neither a `dl` nor a `grant` query, or a GET from a known link-preview bot (facebookexternalhit, Twitterbot, Slackbot and Slack-ImgProxy, WhatsApp, Discordbot, TelegramBot, Googlebot and others, matched by User-Agent) whatever it asks for, unless it is a browser navigation (`Sec-Fetch-Mode: navigate`). The name segment is cosmetic. Page requests get `dist/<lang>/download.html` (by `?lang=` or `Accept-Language`, with `Vary: Accept-Language`) with `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow`: `<html data-state>` is `ready`, `protected`, `unlocked`, `uploading` or `gone`, the attributes `data-once`, `data-risky` (an extension that can run code) and `data-protected` are set where they apply, and `<head>` gets a JSON block `<script type="application/json" id="fyl-state">` (`<` escaped) with `state`, `id`, `name` (null while a protected file is locked), `size`, `type` (a label such as "ZIP archive"), `ext` (badge text, up to 4 characters), `expiresAt`, `once`, `protected`, `risky`, `url` (the link as shared), `downloadUrl` (the link with `?dl=1` for `ready` and an unprotected `uploading`, the grant URL for `unlocked`), `received` and `updatedAt` (`uploading`), `reason` (`gone`: `expired`, `consumed`, `deleted`, `removed`, `quarantined`, `missing` or `busy`), `error` (`protected`: `wrong`, `paused` or null), `triesLeft`, `pausedUntil` and `now` (the server's time when it rendered the page, which the page counts down against). The page answers 200, or 401 after a wrong password and 429 with `Retry-After` while paused; `gone` keeps the error's status (403, 404, 410 or 429). Pages never count a download, open a one-time session, reveal a protected file's name or send `WWW-Authenticate`. A browser navigation that would otherwise get a 503 `uploading`, a 401 challenge or a 403 `quarantined`, 404, 410 or 429 error (such as `?dl=1` on a link still uploading, or an expired grant) gets the page for the transfer's state instead. curl, wget, the CLI and download managers send no `text/html` and get the file or a status directly, and so does a browser with `?dl=1`.

A browser that opens a one-time link gets the page and no session opens; its Download button requests `?dl=1`. Chat previews and mail scanners that fetch links as HTML therefore can't use up the download, but a scanner that runs the page's script and follows the button can. A page that waits for an upload starts a one-time download by itself only while it is visible.

<a id="hotlink-protection"></a>**Hotlink protection.** Browsers say where a request comes from (`Sec-Fetch-Site`) and what it is for (`Sec-Fetch-Dest`). A `/d/` request with `Sec-Fetch-Site: cross-site` or `same-site` and any `Sec-Fetch-Dest` other than `document` (an image, video, audio, track, frame, embed, object, script, style, font or fetch) gets 403 `hotlink` ("fyl.at files can't be embedded on other sites. Open the link instead.") before a download is counted or a one-time session opens; the `same-origin` file headers also keep other sites from embedding a file or reading it with a no-cors fetch. Another site's navigation (`Sec-Fetch-Dest: document`) to a file address (`?dl=1` or a grant) gets the download page instead of the file, so a direct file link posted elsewhere can't skip the page; HEAD gets the page's status and headers. Requests without these headers (curl, wget, the CLI), typed addresses and bookmarks (`none`) and fyl.at's own pages (`same-origin`) are not affected.

<a id="link-previews"></a>**Link previews.** Download pages carry Open Graph and Twitter tags: `og:site_name` fyl.at, `og:title` the file name, `og:description` "<size> · <type> · expires in <time>" ("still uploading" while it is), and `og:url` the link. A protected link (also once unlocked) says "A protected file on fyl.at", and a closed or quarantined one only names the service. A ready image that isn't protected or one-time, at most 8 MB and named `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` or `.avif`, also gets `og:image` = `<link>?preview=1` with `twitter:card` `summary_large_image`. That address answers only known link-preview bots (GET or HEAD, never a browser navigation), and only while the transfer is ready, not protected, not one-time and not quarantined, and its first bytes prove it a PNG, JPEG, GIF, WebP or AVIF image (never SVG). The answer is the picture with its real image type, `Content-Disposition: inline`, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: public, max-age` of at most 300 seconds and never past the expiry, and `Vary: User-Agent`. It counts no download, opens no session and counts against `DOWNLOAD_RATE` like every `/d/` request. Everyone else, and every file that doesn't qualify, gets 404 `not_found`; a browser opening the address gets the download page. Chat apps copy a previewed picture to their own servers, and that copy can outlive the link.

<a id="passwords"></a>**Passwords.** An optional `password` at init protects the download: a string of 6 to 200 code points counted after NFC normalisation, without control characters or lone surrogates (`null` or no field means none; anything else gets 400; `tests/vectors/passwords.json`). The transfer stores only a random 16-byte salt and the PBKDF2-HMAC-SHA-256 hash (100,000 iterations, 32 bytes) of the NFC form. The init fingerprint includes an HMAC of the password keyed with `GRANT_SIGNING_KEY`, so an idempotent replay with another password gets 409. Without that secret a password upload answers 503 `misconfigured`. A protected transfer's `url` is `/d/:id` without the name, and the public `GET /api/transfers/:id` returns `name: null` with `protected: true`; the receipt and the owner keep the name. Requests for a protected file that is ready, page requests aside:

- `?grant=<expiry>.<signature>` from the unlock form, before `expiry` (ms): the file, like an unprotected one.
- `Authorization: Basic …`: the user name is ignored, the password is what follows the first `:`. Right: the file, ranges and one-time sessions as usual, checked on every request. Wrong: 401 with `WWW-Authenticate: Basic realm="fyl.at", charset="UTF-8"` and `Wrong password. N tries left.` as plain text.
- Neither, or a forged, foreign or expired grant (outside a pause): 401 with the same challenge and `This file needs a password. Run: curl -fOJ -u fyl '<url>'`.
- While paused: 429 with `Retry-After` and `Too many wrong tries. Try again in N minutes.`, right password, wrong one or none. A request without a password costs no try, so an open download page asks with one (HEAD `?dl=1`) to see when the pause ends early.

Wrong tries count per transfer and network (a per-transfer hash of the IPv4 address or IPv6 /56). Every value that doesn't match counts, one too short to be valid too; tries during a pause are refused unchecked. 5 wrong tries in a row from one network pause that network for 15 minutes; a right password starts its count over. 50 wrong tries from all networks together within 15 minutes pause the whole transfer for 15 minutes. A client sees its network's pause or the transfer's, whichever ends later. The one exception is the address holding a one-time link's download session (it gave the password, or a grant, when the session opened; its IPv4 address or IPv6 /64, so another /64 of its /56 is not it): the whole transfer's pause doesn't refuse it on `/d/`, the page, the unlock form or `GET /api/transfers/:id` with Basic (which `fyl download` and the encrypted page ask first), only its own network's pause does. Neither pause closes the session: the transfer's doesn't refuse the holder, and its own network's doesn't count as idle time, so the session's 15 minutes run from that pause's end ([one-time links](#one-time-download-sessions)). `curl -fOJ -u fyl 'URL'` asks for the password without echo. HEAD follows the same rules (a wrong Basic password counts there too) and never opens a session.

`POST /d/:id[/:name]` is the page's unlock form: `application/x-www-form-urlencoded` with the field `password`, up to 4 KiB (415 for another type, 413 beyond), counted against `DOWNLOAD_RATE`. It must come from the site: a cross-origin `Origin` or a `Sec-Fetch-Site` other than `same-origin` gets 403, and `Origin: null` passes only with `Sec-Fetch-Site: same-origin`. It answers with the download page: 200 `unlocked` with the name and `downloadUrl` = `<url>?grant=<expiry>.<signature>`, 401 `protected` with `error: "wrong"` and `triesLeft`, or 429 with `error: "paused"`, `pausedUntil` and `Retry-After`; a link still uploading gets the `uploading` page and a closed one the `gone` page. Without `GRANT_SIGNING_KEY` it answers 503 `misconfigured` before a try is counted. A grant expires one hour after it was issued. Its signature is `base64url(HMAC-SHA-256(GRANT_SIGNING_KEY, "fyl-grant:" + id + ":" + expiry))` without padding (43 characters); an expiry more than an hour and a minute ahead is refused. During a key rotation `GRANT_SIGNING_KEY_PREVIOUS` also passes grants that expire within an hour and a minute of `GRANT_SIGNING_KEY_ROTATED_AT`.

<a id="early-links"></a>**Early links.** The `url` from init works at once. While the transfer is being created, uploaded or completed within its 24-hour window, page requests get the `uploading` page and every other request gets 503 `{error, code: "uploading", received, size}` with `Retry-After: 10`, so `curl -fOJ --retry 120 'URL'` waits for the file (add `-u fyl` for a protected one; its password is checked once the file is ready). The public `GET /api/transfers/:id` answers such a transfer with 200 `{id, state: "uploading", size, received, updatedAt, once, protected, name, expiresAt: null, serverTime}`: `received` sums the confirmed parts, `updatedAt` is when the last one finished (or the upload started), and `name` is null for a protected file. The download page polls it every 5 s, then 1.5 times longer up to 60 s while nothing changes (back to 5 s on progress), with ±20 % jitter, not while the tab is hidden, and at least 60 s (or `Retry-After`) after a 429. These public polls count against `STATUS_RATE` (120 a minute per network), not the download limit. Past its upload window the link answers 410 `aborted`.

## End-to-end encrypted transfers

Optional from 2.4.0 and offered to everyone; the normative description is [E2EE.md](E2EE.md). The client encrypts the file as an [age](https://age-encryption.org/v1) file to a fresh X25519 key and uploads only ciphertext; the key travels in the link's fragment, `https://fyl.at/d/<id>#<KEY>` (43 b64url characters), which browsers never send to the server. The server stores a generic name (`fyl-<id[0:8]>.age`), the encrypted size C and two blobs it can't read: `head`, the first 184 bytes of the stored file, and `meta`, the encrypted name and plaintext size. The emergency switch `E2EE_ENABLED` (var in `wrangler.jsonc`, `"true"`) gates only new encrypted inits (403 `e2ee_disabled`); running uploads and existing files keep working when it is off.

- **Init:** `{mode: "e2ee", size: C, e2ee: {head, meta}, expiresIn?, oneTime?, password?, partSize?, clientKey?}` without `filename` (400 if present). C is between 201 bytes and 50 GB and a size an age file of this profile can have; `head` decodes to 184 bytes and `meta` to 712, 1224, 1736, 2248 or 2760, both shaped like age headers with one X25519 stanza, and `meta` reuses none of `head`'s random fields. The answer adds `mode`, and a client that gets no `mode: "e2ee"` back aborts before any part. The idempotency fingerprint covers mode, size, options, head, meta and password, never a name.
- **Pins and parts:** before sending a part's body the client pins its MD5 with `POST /api/upload/pin`: the first value is kept, the same value again answers 200, another one 409 `part_changed`. The part then needs `Content-MD5` (RFC 1864 base64 of the 16 bytes, with its padding) equal to the pin: missing, malformed or unpinned is 400, another MD5 409 `part_changed`, both before R2 and before the attempt counts. R2's ETag must equal the pin afterwards, else 502 `part_corrupt` (the slot and its bytes are freed, one attempt counted). So a resumed upload can never send other bytes under the same nonces; status lists every pin.
- **Completion:** the server compares the stored object's first 184 bytes with `head`; a mismatch deletes the object, fails the upload and answers 409 `head_mismatch`.
- **Downloads:** a browser navigation to any address of the file gets the download page, which decrypts; any other client gets the ciphertext only when it asks for it with `?dl=1`, a grant or Basic, and 409 `encrypted` (plain text: `This file is end-to-end encrypted. Run: fyl download '<url>'`) otherwise, so link unfurlers and plain curl open nothing. The file comes as `fyl-<id[0:8]>.age`, which `fyl decrypt` or `age -d` opens. `fyl download` reads the key from the link (or asks for it) and checks it against `head` and `meta` from `GET /api/transfers/:id` before it requests the file.
- **Passwords:** a protected encrypted transfer gives `head` and `meta` (`e2ee`) only to its owner or with its password as Basic on `GET /api/transfers/:id`; tries count per network as on `/d/`, and a wrong one gets JSON 401 `password_wrong` or 429 `password_paused`, never `WWW-Authenticate`. Its page and the ciphertext take the same Basic header.
- **One-time links:** a whole delivery doesn't close an encrypted one-time link, because decryption or saving can still fail: the session's network may fetch it again (ranges with `If-Range`) until the session idles out after 15 minutes, or the client sends `POST /api/transfers/:id/done` once it verified the last chunk, which closes it at once.
- **Records of a mode this server doesn't know** answer 503 `unsupported_mode` on `/d/` and open nothing.

## Owner API

With the management key (`Authorization: Bearer <key>`), `/api/transfers/:id` answers the owner view: the public fields with the name (also of a protected file), `owner: true`, `serverTime`, and for a protected file `passwordPause: {until, networks, networksUntil}` (the end of the transfer-wide pause or null, how many networks are paused now, and when the last of their pauses ends or null). An upload still running answers 200 with `state: "uploading"`, `expiresAt: null`, `received` and `updatedAt`.

- `PATCH {"expiresIn": seconds}` sets a new lifetime, counted from the original completion; 400 if it has already elapsed.
- `PATCH {"clearPause": true}`, on its own, lifts every password pause at once, each network's and the transfer's. It tries no password and counts as none.
- Both answer the owner view with `serverTime`; while the upload still runs they answer 409 `upload_running`, for a closed transfer 410 with its reason, while quarantined 403 `quarantined`.
- `DELETE` closes the transfer for everyone and deletes the bytes; it works while the upload runs and while the file is quarantined.

The resume token gets 403 `denied` on all of these.

## Reports

`POST /api/reports` (JSON up to 16 KiB, same-origin rules as other mutations, `REPORT_RATE` 5 a minute per network) files a case about a transfer:

| Field | Rule |
| --- | --- |
| `link` | The download link (`https://fyl.at/d/<id>` or `/d/<id>/<name>`, optionally with `?dl=1` or a grant) or the bare id. Other hosts, credentials, fragments, dot segments and backslashes get 400 `invalid_link`. The link is never fetched and only the transfer id is kept. |
| `category` | `malware`, `phishing`, `csam`, `illegal`, `copyright`, `privacy` or `other` (else 400 `invalid_category`) |
| `details` | 20 to 4000 code points after trimming, no control characters except line breaks and tabs (else 400 `invalid_details`) |
| `name`, `email` | Up to 200 characters and a plain `x@y.z` address of up to 254; required unless the category is `csam` (DSA Art. 16(2)(c); else 400 `invalid_name` or `invalid_email`) |
| `goodFaith` | Must be `true` (DSA Art. 16(2)(d); else 400 `good_faith_required`) |
| `turnstile` | While Turnstile is on: the token of the page's Turnstile widget, a string of at most 2048 characters (else 403 `turnstile_failed`). Ignored while it is off |

<a id="turnstile"></a>Turnstile is on when the var `TURNSTILE_SITE_KEY` (the public site key, committed in `wrangler.jsonc`) and the secret `TURNSTILE_SECRET` are both set; production has it on from 2.3.0. `/config.js` then hands the page `turnstileSiteKey`, and the page renders the widget (action `report`) and sends its token. The Worker checks the other fields first, so a typo doesn't use up the token, then sends the secret, the token and the client's address to Cloudflare's siteverify. The token must pass, have been solved on the report host (`REPORT_HOST`, `report.fyl.at`; `PUBLIC_BASE_URL`'s host where there is none, as in local development) for the action `report`, and be at most 5 minutes old; anything else gets 403 `turnstile_failed` (the error-code `timeout-or-duplicate` included: a token is good for one check, so the page gets a new one after every answer). Answers to Cloudflare's test secret keys skip the host and action checks. Siteverify unreachable (10 s timeout), not 2xx, unreadable or reporting `internal-error`: 503 `temporarily_unavailable`, so the check fails closed. A secret Cloudflare calls invalid or missing: 503 `misconfigured`. Only then is the link looked up, so an unknown link with a good token gets 404. While the check is on, a report sent without the page (curl, scripts) gets 403; the Worker asks for Turnstile on no other route.

It answers 201 `{case, received, fileAvailable}`: `case` is an id like `R-7K3M9Q2XPA` (Crockford base32), `received` the time in ms. A transfer that closed but whose tombstone still exists (up to 7 days after cleanup) is accepted with `fileAvailable: false`; one that was taken down is stored as a closed case with outcome `removed`; an id nothing is known of gets 404 `not_found`. A network may file 50 cases a day (429 `report_limit`). Each case keeps the transfer id, category, details, name and email if given, the day's network hash and its events, until 183 days after it closed. The operator decides each case; an open case on a file that is gone closes by itself (outcome `expired`, or `removed` after a takedown), at the latest about 8 days after it was filed.

## Operator API

The operator API lives on the admin host `https://admin.fyl.at`, behind Cloudflare Access: every request there needs Access's signed token (`Cf-Access-Jwt-Assertion`, added by Access after a sign-in or for the service token sent as `CF-Access-Client-Id` and `CF-Access-Client-Secret`), which the Worker verifies too; without it 403 `access_denied`, whatever the path. On `https://fyl.at` these routes answer 404.

Operator routes require `Authorization: Bearer <ADMIN_TOKEN>` and exist only when that secret has at least 32 characters (otherwise 404); a wrong token gets 401 `denied`. `GET /api/admin/ready` also accepts the read-only `MONITOR_TOKEN` (exists when either secret is set); on the admin host that token also reads `GET /api/billing` ([below](#billing-estimate)), and nothing else. On the admin host an Access identity listed in the `ADMIN_EMAILS` secret (the operator's browser) reads `GET /api/admin/ready`, `GET /api/admin/uploads` and `GET /api/admin/reports` (and the dashboard's `GET /api/stats` and `GET /api/billing`) without a token; its report listing leaves out `details`, `name`, `email`, `network`, `transferId`, `updatedAt` and `closedAt`. Everything else needs the token. All have their own rate limit, `ADMIN_RATE` (10 a minute per network, checked before the token), except the operator's token-free reads. `npm run admin` wraps them ([runbook](OPERATIONS.md#reports-abuse-and-incidents)).

| Route | Method | Body | Answer |
| --- | --- | --- | --- |
| `/api/admin/ready` | GET | | Readiness, 200 when every check passes, else 503 (below) |
| `/api/admin/uploads` | GET; POST | POST `{"paused": bool}` (≤ 256 bytes) | `{paused, stored, today, network, overdueCleanups, networkHashKeyed, openReports}` |
| `/api/admin/reconcile` | POST | | `{drift: {aggregate: difference}}` after the Budget's sweep and reconciliation |
| `/api/admin/takedown` | POST | `{id, note}` (≤ 8 KiB) | `{removed: true, existed}`, plus `reportsUpdated: false` if the open cases could not record it |
| `/api/admin/quarantine`, `/api/admin/restore` | POST | `{id, note}` (≤ 8 KiB) | The transfer view (below), plus `reportsUpdated: false` if the open cases could not record it |
| `/api/admin/transfers/<id>` | GET | | `{id, exists, status, name, size, createdAt, expiresAt, once, protected, quarantine, clean, openReports, openCases}` |
| `/api/admin/reports` | GET | query `status` (`open` default, `closed`, `all`), `limit` (1–200, default 50), `after` (a case id), `transfer` (an id) | `{reports: [case, …], next}` |
| `/api/admin/reports/<case>` | GET | | The case with `events: [{at, action, note}]` |
| `/api/admin/reports/<case>` | POST | `{action, note}` (≤ 8 KiB) | The case with its events and `transfer: {status, quarantine}` (null if the transfer didn't answer) |

- `stored` is `{bytes, payload, copies, reserved, uploads, maxBytes, maxUploads}` (`bytes` is what `MAX_STORED_BYTES` checks), `today` is `{bytes, payload, reserved, attempted, uploads, maxBytes, maxUploads}` for the UTC day, `network` is `{maxBytes, maxUploads, maxActive, maxStored}`. `overdueCleanups` counts reservations still active 8 days and an hour after admission. While paused, new uploads and every part request answer 503 `uploads_paused`.
- Every quarantine, restore, takedown and every decision except `note` needs a `note` of 3 to 1000 characters (400 `note_required`). The API accepts a `note` action with an empty note (up to 1000 characters); `npm run admin` requires text.
- A takedown is final: the transfer answers 410 `removed` for good and its id never takes an upload again. An id without a transfer can be taken down too (`existed: false`). Quarantine answers 409 `closed` for a closed transfer; restore answers 409 `removed` after a takedown and 409 `not_quarantined` when there is nothing to lift.
- `openReports` and `openCases` (the first 20 open case ids in queue order) are null when the Reports object didn't answer; the view still works.
- A case is `{case, createdAt, transferId, category, details, name, email, network, status, outcome, updatedAt, closedAt, priority, fileAvailable}`. `status` is `open` or `closed`; `outcome` is `removed`, `restored`, `rejected` or `expired`; `priority` is 1 (CSAM), 2 (malware, phishing), 3 (illegal, privacy) or 4 (copyright, other). The open queue is sorted by priority, then oldest first; closed and all cases newest first. `next` is the last case of a full page, to pass as `after`; a cursor whose case is gone gets 400 `invalid_cursor`.
- Decisions: `quarantine` (the case stays open), `restore` (closes as `restored`), `remove` (the takedown; closes as `removed`), `reject` (closes as `rejected`; the transfer stays as it is) and `note` (adds an event, also to a closed case). A decision on a closed case gets 409 `closed`; rejecting the last open case of a quarantined transfer gets 409 `quarantined` (restore or remove decide it). Events record `received`, every action with its note, and the outcome when a case closes by itself.

Readiness answers `{ready, attention, reasons, checks, turnstile, e2ee, paused, backlog, capacity, openReports, oldestOpenReportAge, highestOpenPriority, version}`:

- `checks`: `secrets` (`NETWORK_HASH_KEY`, `GRANT_SIGNING_KEY`, `ADMIN_TOKEN`, each true when set with at least 32 characters), `rotation` (false while `GRANT_SIGNING_KEY_PREVIOUS` is set without a rotation time or more than an hour and a minute after it), `r2` (a `head` of `health/ready` doesn't throw; the object need not exist), `budget` and `reports` (the objects answer). `ready` is true only when all pass.
- `reasons` lists what waits for the operator: `open_reports`, `overdue_cleanups`, `storage_60` (stored bytes reached 60 % of `MAX_STORED_BYTES`) and `daily_60` (today's payload and reserved bytes reached 60 % of `MAX_DAILY_UPLOAD_BYTES`); `attention` is true when any is present. Readiness doesn't depend on them.
- `turnstile`: `on` (`TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET` set, the report form checks [Turnstile](#turnstile)), `off` (neither) or `incomplete` (only one, so the form doesn't check). It changes neither `ready` nor `reasons`, and it can't tell Cloudflare's test secret keys from a real one.
- `e2ee`: `on` while `E2EE_ENABLED` takes new encrypted uploads, else `off`; like `turnstile` it changes neither `ready` nor `reasons`. `paused`: true while `npm run admin -- pause` holds new uploads, null when the Budget didn't answer; no check or reason either.
- `version`: `{tag, deployedAt}` of the live Worker version from the version metadata binding (`tag` as `npm run deploy` names it, `v2.4.1`; `deployedAt` when it was uploaded, ISO 8601), each null where the binding says nothing usable; null without the binding.
- `backlog.overdueCleanups`, `capacity.storedPercent` and `capacity.dailyPercent` (whole percent, rounded down), `capacity.storedBytes` and `capacity.maxStoredBytes` (the bytes `MAX_STORED_BYTES` checks: stored payload, copies and reserved bytes of uploads not yet cleaned up, and that limit; the dashboard's "Storage in use"; only the local dashboard's own read, a `*.localhost` admin host with `DEV_FAKE_STATS`, gets made-up bytes there, marked `capacity.sample: true`), `openReports`, `oldestOpenReportAge` (seconds) and `highestOpenPriority`; null where a check failed. Counts and percentages only, never ids, names or keys.

## Statistics

`GET /api/stats?range=1d|7d|30d|90d` (default `7d`) on the admin host, for the operator's Access identity or with `ADMIN_TOKEN`: aggregates of `fyl_events` from Analytics Engine's SQL API (counts are `SUM(_sample_interval)`), cached 60 seconds per Cloudflare location. 400 for another range, 503 `stats_unconfigured` without the Worker secret `CF_ANALYTICS_TOKEN`, 502 `stats_unavailable` when the SQL API fails.

A visitor is a browser page view that named a language; everything else is automated traffic. fyl's own uploads and downloads (client `own`) are left out of every figure and counted apart.

- `series`: every bucket of the range, oldest first, `{t, pageViews, homeViews, automatedViews, uploads, uploadBytes, webStarted, webUploads, downloads}` (`t` is `YYYY-MM-DD` or `YYYY-MM-DDTHH`).
- Lists of `{name, n}`, largest first, at most 20: `pages` (`home`, `report`, `privacy`, `download`, `gone`), `closedReasons` (why a closed link closed, visitors only), `referrers` (a host, `direct`, `ip`, `private`, `other`; fyl.at's own pages are in `ownReferrers` `{download, report, site, unsplit}`), `countries`, `devices`, `languages`, `clients` (all page views, `script` for a browser's name without a language), `downloadsByClient`, `uploadsByClient`, `uploadsStarted`, `uploadOptions` (`password`, `once`, `e2ee`, `none`; they combine), `cliFetches` (`install` or a platform), `reportsByCategory`, `budgetRefused`, `rateLimited`, `turnstileFailed`, `cleanupRetry`, `accessDenied`; `downloadsPerTransfer` (`0`, `1`, `2–5`, `6–20`, `>20`) and `uploadSizes` (`{name, n, bytes}`) in their own order; `campaigns` is `[{source, campaign, n}]`, `outcomes` `[{name, n, gbDays}]`, `lifetimes` `[{seconds, n}]`.
- `passwords` `{ok, wrong, paused}`, `moderation` `{quarantine, restore, takedown}`, `previewServed` `{n, bytes}`, `misconfigured` (a count), `performance`, `health` and `counters` (every event and code of the range with its count and total).

## Billing estimate

`GET /api/billing` on the admin host, for the operator's Access identity, with `ADMIN_TOKEN`, or with the read-only `MONITOR_TOKEN` for the hourly monitor's alert (`scripts/monitor.py`; `ADMIN_RATE` for either token). `MONITOR_TOKEN` opens no other route here: `/api/stats` and every operator route but readiness answer it 401, any other method on `/api/billing` 405, and `https://fyl.at/api/billing` doesn't exist (404) whatever the token. The answer: an estimate of the current Cloudflare billing cycle so far, for the whole account, from one GraphQL Analytics request with the Worker secret `CF_ANALYTICS_TOKEN` (the Worker's errors come from a second one, best effort), priced with the table in [COSTS.md](COSTS.md#prices-and-the-dashboards-estimate). Not the invoice. Cached 15 minutes per Cloudflare location. 503 `billing_unconfigured` without the secret or when `BILLING_CYCLE_DAY` is no day of the month, 503 `billing_refused` when Cloudflare refuses the secret (GraphQL answers HTTP 400, 401 or 403, or the error code `authz`: expired, revoked or without Account Analytics Read), 502 `billing_unavailable` when GraphQL fails otherwise or answers another error; none of them affects `/api/stats`, and none is cached.

- `generatedAt` (ms), `sample` (true only for local development's made-up data), `pricesAsOf` (`YYYY-MM-DD`, when the prices were checked), `currency` (`USD`).
- `cycle`: `{day, start, end, days, elapsedDays}`; `start` and `end` are the first and last day (`YYYY-MM-DD`, UTC), `days` the cycle's length, `elapsedDays` the days so far with today.
- `meters`, in this order: `workerRequests`, `workerCpu`, `r2Storage`, `r2ClassA`, `r2ClassB`, `objectRequests`, `objectDuration`, `rowsRead`, `rowsWritten`; each `{id, product, name, unit, used, included, step, price, billedSteps, cost}`. `unit` is `requests`, `ms`, `GB-month` (10⁹ bytes; each day's peak of payload and metadata added up over the days so far, divided by the cycle's days), `operations`, `GB-s` or `rows`; `price` is dollars per `step` of usage above `included`, `billedSteps` that usage rounded up to whole steps, `cost` the dollars for it (0 within the allowance).
- `base` (5, the Workers Paid minimum), `aboveAllowance` (the meters' costs) and `total` (both), in dollars.
- `pace` (the whole cycle at the same daily rate, in dollars), `storageByDay` (`[{date, bytes}]`, each UTC day's R2 peak) and `workerErrors`: the `fyl-at` Worker over the last 24 hours, `{since, requests, errors, statuses: [{name, n}]}` (`errors` are requests that ended in an exception, exceeded limits or an internal error; `statuses` the outcomes other than `success`, `clientDisconnected` included), or null when their own request failed or gave no such list (the estimate answers all the same). Not billed, and the billed meters stay account-wide.

## Clients

Both clients upload 50 MiB parts (the browser four at a time, the CLI four by default and up to eight), retry by the [error classes](#errors), and accept a completion only with a valid [receipt](#receipt). The CLI checks every part's ETag against its own MD5 right after sending it. The browser checks the finished parts' ETags only when it resumes (in a Web Worker), and sends again the parts that differ or can't be checked.

- **Folders.** Both clients send a folder as one deterministic, uncompressed zip `<folder>.zip` ([FOLDER-ZIP.md](FOLDER-ZIP.md)); the server sees an ordinary file of that name and size, so nothing on this page changes for it. A resumed folder upload carries the folder's fingerprint in the CLI's resume value and the browser's record, and is refused when the folder changed.
- **Printed links (CLI, 2.5.0).** The CLI prints the receipt's `url` and `managementUrl` only when they are plain printable ASCII `https` links (`http` only on loopback), the management link only as `<origin>/#manage/<id>/<key>` with a 43- to 64-character ID and a 43-character key; otherwise it prints no link and exits 1, the upload complete. Server `error` texts are shown with control characters removed.
- **Updates (CLI, 2.5.0).** After a command that succeeded (not `fyl decrypt`), at most once a day and only when stderr is a terminal, the CLI reads `/cli/version.json` of its endpoint's origin with a 2-second limit and says on stderr when a newer version exists. The request carries only the User-Agent; the CLI stores only the time of the check (`update-check` in its cache folder). `FYL_NO_UPDATE_CHECK=1` or a set `CI` turns it off. `fyl update` downloads `/cli/<version>/<binary>` and accepts it only with the SHA-256 that `version.json` and that folder's `SHA256SUMS` both name ([CLI](CLI.md#install-and-update)).
- **Resume.** An interrupted upload continues within its 24-hour window: `/api/upload/status` lists the confirmed parts, the client re-checks each against the local file by MD5 and sends only the rest; an upload that already completed replays its completion. A part whose ETag isn't an MD5 (32 hex digits) can't be checked: the browser sends it again, and the CLI accepts it only from an API on this machine (the `wrangler dev` R2 simulator) and otherwise sends it again ([CLI](CLI.md#interrupted-uploads)).
- **The web client** keeps an interrupted upload with its key, but not its password, in `localStorage` (`fyl-upload`) until the upload window ends, so it survives closing the tab. Each upload holds the Web Lock `fyl-upload:<uploadId>` while it runs, a resume takes that lock only if it is free and re-reads the record inside it, and new uploads are created under the lock `fyl-new-upload`, so two tabs never continue or replace the same upload; without Web Locks nothing resumes by itself and a resume runs once per page load. It resumes only when name, size, date and a SHA-256 fingerprint of the first and last MB plus the size match, with the upload's own expiry, download mode and password; without WebCrypto (plain HTTP other than localhost) nothing is kept. Finished parts are checked in a Web Worker ("Checking uploaded parts… N %"). A part request counts as dropped after 120 seconds without upload progress. The record goes only after the receipt is stored in the recent list.
- **Browser storage.** Recent uploads with their management links stay in `localStorage` (`fyl-recent`, up to 20, each until forgotten or a day after its link expires); download passwords stay in the tab's `sessionStorage` unless "Remember the password on this device" is ticked (`fyl-passwords`). Keys of encrypted uploads stay in the tab's `sessionStorage` (`fyl-keys`), in `localStorage` only while "Remember keys on this device" is ticked; an interrupted encrypted upload's record keeps each part's MD5 but never the key. A recipient's typed key that verified stays in that tab's `sessionStorage` (`fyl-open-keys`). "Forget this device" clears recents, kept passwords and keys and an idle interrupted upload.

The User-Agent is never authentication; its only effects are that known preview bots get the download page or the image preview, and the kind of client counted in `download_started`. The CLI sends `fyl-cli/<version>`, plus `FYL_UA_SUFFIX` when that is a plain token of up to 40 characters (`A-Z a-z 0-9 . _ / -`); fyl's own checks set `fyl-smoke`, which the statistics count as fyl's own.
