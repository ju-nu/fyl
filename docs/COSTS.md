# Cloudflare cost model

Planning estimate, verified against Cloudflare's published pricing on 2026-10-27. USD before tax; not a billing guarantee.

Assume 100,000 files of 100 MB each: 10 TB uploaded per 30-day month, evenly distributed, with one full download each. At 50 MiB parts this is two parts/file, roughly 400,000 R2 Class A operations (create + two parts + complete) and 100,000 Class B download operations. Both fit the monthly R2 free operation allowances if those allowances are otherwise unused. R2 Standard internet egress is free, including these 10 TB of downloads.

Retention determines storage cost:

| Average retention | Average resident storage | Approx. R2 storage/month |
| --- | ---: | ---: |
| 5 minutes | 1.16 GB | $0 within free allowance |
| 24 hours | 333 GB | $4.85 |
| 7 days | 2,333 GB | $34.85 |
| 10 TB resident for the entire month | 10,000 GB | $149.85 |

Calculations use $0.015/GB-month after an otherwise unused 10 GB-month allowance. Billing rounding, other account usage, incomplete uploads and cleanup timing can change the result. The last row describes resident storage, not the normal temporary-file workload.

fyl.at runs on Workers Paid. Uploads and downloads stream natively, so CPU per request stays in milliseconds. Workers Paid starts at $5/account/month and includes 10 million requests and 30 million CPU milliseconds; SQLite Durable Objects have separate included request, duration and database allowances. Static files are served by Workers Static Assets, but the Worker runs first for every request (`run_worker_first: true`, so the admin host checks Cloudflare Access before any file): each page, script, font and CLI download also counts as one Worker request, which hands the file to the asset binding without reading it. A $5 base plus the table's R2 storage is a useful starting estimate only while Worker/DO/database/log/build usage stays within the applicable allowances. Measure duration/CPU; do not infer a complete bill from byte volume alone. The Analytics Engine counters write data points per event, never per chunk: about five per upload (completion, lifetime, completion time, cleanup age, GB-days), one per confirmed or failed part, one per download start, one per password check (`password_ok`, `password_wrong`, `password_paused`), one per waiting page or 503 `uploading` (`early_wait`; `curl --retry` counts each try), one or two per refused request and one per page view (`page_view`: the home page, the report form, the privacy page and every download or closed-link page). At the caps (50,000 uploads and 1 TB a day) that is roughly 8 million points a month before the page views; check it against the Analytics Engine allowance. A browser opening a link costs one Worker request and Durable Object call for the download page before the download itself. A page waiting for an upload polls `GET /api/transfers/:id` every 5 seconds while parts arrive and backs off to once a minute while nothing changes (per visible page about 720 requests an hour, up to about 900 with the jitter, plus one each time the tab becomes visible again; hidden pages don't poll). A password check runs PBKDF2 with 100,000 iterations in the transfer's Durable Object on every Basic Auth request and unlock, so protected downloads split into many range requests cost more CPU than plain ones. A closed transfer's Durable Object storage is dropped 7 days after cleanup; only takedowns keep their small record for good. A Free account has daily request/CPU limits rather than the Paid allowances.

The live caps are 1 TB/day received and 5 TB stored (binary units, settings in `wrangler.jsonc`), so the assumed 10 TB/month workload fits: 7-day retention needs about 2.33 TB of storage. At the storage cap, R2 storage alone costs about $82/month (5 TiB ≈ 5,498 GB × $0.015). At the daily cap, about 21,000 part uploads per day plus each upload's create and complete (100 MB files) come to about 1.3 million Class A operations a month, just over the monthly allowance; R2 bills each started million, so that adds $4.50 a month ([rounding](#prices-and-the-dashboards-estimate)). A Cloudflare budget alert at $20 of usage charges fires at roughly 1.34 TB average resident storage.

## Cost alerts

fyl's caps limit what the service admits, not what Cloudflare bills, and none of these products has a spending limit. Two alerts should watch the bill; the figures below assume an account budget alert at $20 and the monitor's default of $15:

- **Cloudflare's budget alert** (account-wide, set by the operator in the Cloudflare dashboard, here $20) fires once the cycle's usage charges reach $20: Cloudflare describes the alert type (`billing_budget_alert`, threshold `total_spend_dollars`) as "Notifies when your usage charges reach your configured budget threshold for the billing period". Taking the $5 base as no usage charge, as the 1.34 TB above does, that is an invoice near $25. With the caps allowing about $82 a month of R2 storage alone, a cycle can be well on its way to $87 before it says anything, and it doesn't say which meter.
- **The Monitor workflow's billing alert** (hourly, [monitor](OPERATIONS.md#monitor)) reads the dashboard's estimate below (`GET /api/billing`) and fails the run, so GitHub mails the operator, once the estimated total so far reaches `BILLING_ALERT_USD`: **$15** by default, the $5 base plus $10 above the allowances (on its own, about 677 GB-month of R2 storage, or more than 3 million Class A operations). The planned workload with 24-hour retention ($4.85 of storage, $9.85 with the base, table above) stays below it; 7-day retention ($39.85) crosses it. With the storage cap full from the cycle's first day, the estimate passes $15 on day 4 of 31 (709 GB-month so far), and that run's `Pace:` line already shows about $87 for the cycle (the dashboard's "This billing cycle" shows the same pace, computed alike in `src/billing.ts`). The mail names the total, the dearest meters and the invoice link, and comes every hour until the cycle starts over or the alert is raised. The estimate leaves out tax and a few products (below), so the invoice is a little higher than the figure it alerts on.

Keep the monitor's alert below the account's budget alert, so the monitor mails first whether or not Cloudflare counts the base as usage. It is `BILLING_ALERT_USD`, a variable of the GitHub environment `monitor` ([how to change it](OPERATIONS.md#monitor)); without it the monitor uses 15.

How the estimate reads them:

- **Rounding.** Cloudflare rounds usage up to the next billing unit: R2 "1,000,001 operations are billed as 2 million", "1.1 GB-month as 2 GB-month"; Durable Objects round the usage above the allowance ("500,000 GB-s … rounded up to 1,000,000 GB-s", 1.5 million requests cost $0.15). The Workers page names no rounding; the estimate rounds it the same way. Every allowance is a whole number of steps, so both readings give the same dollars.
- **R2 storage** is GB-month: "averaging the peak storage per day over a billing period". The estimate adds each UTC day's peak (payload plus metadata, the buckets' peaks summed) and divides by the cycle's days, so "so far" grows into the month's average. 1 GB is taken as 10⁹ bytes: the R2 page doesn't say, the Durable Objects examples compute with 1 GB = 1,000 MB, and this file always assumed it. fyl's own sizes (the budgets, the dashboard's "Storage in use") are binary, so 5 TB of `MAX_STORED_BYTES` is about 5,498 billing GB.
- **R2 operation classes** as the R2 page lists them. Class A: ListBuckets, PutBucket, ListObjects, PutObject, CopyObject, CompleteMultipartUpload, CreateMultipartUpload, LifecycleStorageTierTransition, ListMultipartUploads, UploadPart, UploadPartCopy, ListParts, PutBucketEncryption, PutBucketCors, PutBucketLifecycleConfiguration. Class B: HeadBucket, HeadObject, GetObject, UsageSummary, GetBucketEncryption, GetBucketLocation, GetBucketCors, GetBucketLifecycleConfiguration. Free: DeleteObject, DeleteBucket, AbortMultipartUpload. Types the page doesn't list (the analytics also show GetBucketSippyConfiguration and GetBucketNotificationConfiguration from the dashboard) count as Class B when they start with Get or Head, otherwise as Class A.
- **Data:** one GraphQL Analytics request for the whole account (no script or bucket filter): `workersInvocationsAdaptive` (requests, `cpuTimeUs`), `r2StorageAdaptiveGroups` (daily max of `payloadSize` and `metadataSize`, Standard), `r2OperationsAdaptiveGroups` (requests by `actionType`, Standard), `durableObjectsInvocationsAdaptiveGroups` (requests of every type) and `durableObjectsPeriodicGroups` (`duration` in GB-s, `rowsRead`, `rowsWritten`). Each keeps 90 days and answers at most 32 days per query (checked 2026-10-31). `durableObjectsStorageGroups` returns nothing for SQLite-backed objects, so stored data is left out.
- **Not included:** Workers Analytics Engine, Workers Logs, Workers Builds minutes, Durable Objects stored data, R2 Infrequent Access, other products (KV, D1, Queues, …) and subscriptions, tax. The real invoice is on the dashboard's billing page (*Open billing*).
- **First reading** (2026-10-31 00:20 UTC, day 4 of the cycle from 2026-10-28): 8,232 Worker requests, 31,338 CPU ms, 0.98 GB-month of R2 storage (daily peaks of 16.0, 13.2 and 1.2 GB), 1,451 Class A and 378 Class B operations (167 free), 5,172 Durable Object requests, 100 GB-s, 100,717 rows read and 14,485 written: everything within the allowances, $5.00 so far.
